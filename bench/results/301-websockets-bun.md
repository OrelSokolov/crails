# 301-websockets — bun publish/send vs CRails transport (оригинальный bench oven-sh/bun)

Оригинал: https://github.com/oven-sh/bun/tree/main/bench/websocket-server
(«Running a WebSocket chat server, 32 clients broadcasting, messages per
second»). Сервер: чат — клиент шлёт текст, сервер рассылает `name: msg`
всем 32 клиентам. Клиент: оригинальный `chat-client.mjs`, запускается
одним bun-процессом (32 клиента × 1664 сообщений за раунд, рестарт по
получению всех эхо, минимум 64 ms между раундами; 10 секундных замеров,
медиана; в таблице — медиана медиан трёх полных проходов).

Окружение: Intel Core Ultra 7 155H (22 ядра), 32 GB RAM, Linux 6.19.14.
Bun 1.3.8 (1.4 не ставили — по решению пользователя; контрольный прогон
на 1.4 можно добавить позже), Node v20.19.1 (у Bun в оригинале 26.7.0), ws 8.22.0.
Копия бенчмарка и раннер: `bench/bun_ws/` (`run_all.sh`).

## Данные

| сервер | путь доставки | msgs/s (медиана) | peak RSS |
|---|---|---:|---:|
| Bun 1.3.8 (`publishText`, топик) | encode-once + нативный fanout | **2 396 657** | 44–57 MB |
| **Crystal stdlib** (`MODE=frame`) | фрейм кодируется 1 раз, запись тех же байтов в каждый сокет | **1 246 495** | 13–17 MB |
| **Crystal stdlib** (`MODE=send`) | per-connection `ws.send` | **1 267 526** | 13 MB |
| Bun 1.3.8 (`send` в цикле) | per-connection `ws.send` | 412 926 | 44–60 MB |
| Node v20 + `ws` 8.22.0 | per-connection `ws.send` | 220 944 | 56–84 MB |

Медианы по трём проходам: bun-publish 2401k/2397k/2395k; bun-send
385k/411k/413k; node 198k/221k/240k; crystal-frame 1256k/1246k/1235k;
crystal-send 1172k/1268k/1327k. Потерь нет (клиент дожидается полного
раунда эхо, иначе завис бы).

## Откуда у Bun 4.17M (их диаграмма)

Разрыв 4.17M против 159K внутри самого Bun — это не «Bun быстрее Node»,
а **два разных API**:

- `ws.publishText(topic, msg)` — подписки на топик ведёт нативный слой;
  сообщение кодируется в WebSocket-фрейм один раз, и те же байты
  сбрасываются в сокеты подписчиков батчами напрямую из нативного кода,
  минуя JS-колбэк на каждого получателя.
- `ws.send()` в цикле по клиентам — на каждого получателя отдельный вызов
  с валидацией строки, UTF-8 encode и построением фрейма; отсюда 159K —
  уровень Node/Deno (123–124K у них).

На этой машине publish даёт ~2.4M (не 4.17M — другой CPU: у Bun в
оригинале AMD EPYC 9R14, и версия 1.4 против нашей 1.3.8).

## Вывод

- Transport-слой CRails (Crystal HTTP::Server + stdlib WebSocket,
  fiber-per-connection — тот же стек, на котором работает
  action_cable_cr): **~1.25M msgs/s** — в ~2.5–3× медленнее bun publish,
  в **3× быстрее** bun send и в **5–6×** быстрее Node ws, при 13–17 MB
  RSS против 44–84 MB.
- Crystal `send` ≈ `frame`: на 32 клиентах узкое место не кодирование
  фрейма, а чтение входящих masked-фреймов и планирование файберов.
  Encode-once начнёт отрываться на сотнях коннектов.
- Bun publish остаётся быстрее: у него fanout целиком в нативном коде,
  без захода в fibers/шелл колбэков на каждого получателя. Подобный
  fast-path (нативный батч-write готового фрейма по списку подписчиков)
  — кандидат на оптимизацию action_cable.cr, если понадобится.

Сравнение с полным Action Cable протоколом (JSON-конверты, подписки) —
в `300-websockets.md`: CRails 261k против Rails 6.7k.
